# CineVerse Security Architecture & Threat Mitigations

## 1. Authentication & Session Management

### 1.1 Password Hashing & Bcrypt Compliance
Passwords are hashed using standard `bcrypt` with salt rounds compliant with production guidelines. Modern `bcrypt` limits passwords to 72 bytes; CineVerse validates password length strictly before hashing to prevent wrapping attacks.

### 1.2 JWT Tokens & Dual-Token Rotation
- **Access Tokens**: Short-lived JSON Web Tokens signed with HS256 containing `sub` (User ID), `role`, and `exp` (60 minutes).
- **Refresh Tokens**: Cryptographically secure UUIDs persisted in the database with revocation capabilities and 30-day longevity.
- **Pluggable SMS OTP**: Development fallback uses in-memory or Redis key-value storage with 5-minute expiry and attempt-rate limiting.

---

## 2. Role-Based Access Control (RBAC)

FastAPI dependencies enforce least-privilege access across endpoints:
- **`customer`**: Can search catalog, hold seats, manage own bookings, and request cancellations.
- **`support`**: Read-only access to customer bookings and refund logs.
- **`cinema_manager`**: Can modify showtimes, configure price rules, and review cinema screen occupancy.
- **`admin`**: Full administrative privileges, including `/api/v1/admin/analytics` and platform audit logs.

## 3. Financial Integrity & Payment Security

### 3.1 Razorpay HMAC SHA-256 Verification
When a payment transaction completes, the backend validates the signature generated by Razorpay:
```python
expected = hmac.new(
    settings.RAZORPAY_KEY_SECRET.encode(),
    f"{order_id}|{payment_id}".encode(),
    hashlib.sha256
).hexdigest()
is_valid = hmac.compare_digest(expected, signature)
```
Using `hmac.compare_digest` prevents timing attacks.

### 3.2 Webhook Idempotency & Replay Protection
Payment webhook events (`payment.captured`, `order.paid`) are logged in the `payment_events` table indexed by `event_id`. If an event ID has already been processed, the backend returns `200 OK` immediately without duplicate booking settlements or double ticket generation.

## 4. Cryptographic E-Ticket Admission Verification

### 4.1 Anti-Counterfeit HMAC QR Signatures
Each issued ticket contains a cryptographic HMAC SHA-256 signature generated with server-side secrets:
```python
signature = hmac.new(
    settings.QR_SIGNATURE_KEY.encode(),
    f"{booking_code}|{showtime_id}|{seat_ids}".encode(),
    hashlib.sha256
).hexdigest()
```
When scanned at an auditorium entrance, scanners verify the signature against the booking payload. Even if a bad actor attempts to tamper with admission seat numbers or copy a ticket code, the cryptographic verification fails immediately.

## 5. Concurrency Race Condition Mitigations

### 5.1 Atomic Check-and-Set
Double-booking vulnerabilities are eliminated through atomic row-level locks on `seat_inventory`:
- Multiple parallel clients requesting the exact same seat within the same millisecond are serialized at the database level. Exactly one client obtains the hold; all other clients receive `409 Conflict` or a friendly `Seat already held` notification.
- Holds expire automatically after 300 seconds through both Redis TTL and the asynchronous SQL sweeper task.
